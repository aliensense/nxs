# Changelog

All notable changes to NXS: the `nxs` tool and daemon, the `libnxs` runtime library, the NXS unit firmware, the personalities and images, and the descriptor pack. The format follows Keep a Changelog; the versions follow the release tags.

## [Unreleased]

### Added

- The guides on the documentation site read as getting-started pages: the NVIDIA Jetson deployment guide, Getting started with the NXS unit, Multi-sensor dashboard on ROS 2, Custom sensor personality and Custom camera personality, each with a version driven from an AI agent, and a landing page that lists them. The hotfix refusal on JetPack 7.2.1 names the deployment guide.
- Camera personalities. The unit on a camera's pod stores the image sensor's program as a sealed image and runs it on the pod's bus. It serves the sensor's modes, controls and capture facts back to the host as records, so the host carries no sensor source.
- The camera personalities of the two shipped Sony heads, a global-shutter and a rolling-shutter one. On 2 CSI lanes the global-shutter head runs 1920x1080 RAW10 from 1.50 to 160.49 fps alone and to 80.13 fps as a pair, and the release proves the frame-synced pair at 30 and 50 fps on 2 CSI lanes and at 60 fps on 4. The rolling-shutter head runs 1920x1080 RAW10 alone from 1.50 to 59.84 fps.
- `nxs <port> <link> upload <name>` puts a camera personality in the pod's store. A unit holds one camera personality: an upload replaces it, and `--slot` puts it in another slot.
- A camera link without a pod. The host runs the sensor's sealed image through the hub by the same steps a pod takes. A pod adds the unit's samples and time sync.
- A hub link that declares a pod and no camera comes up with the pod alone. `nxs <port> status` reads `cam0/A: pod unit-cam0-a (fxos8700), up` for it.
- The hub's and the serializer's programs ship as sealed images in the assets tarball. The host runs them through `libnxs` when it brings a port up.
- Under frame sync the exposure is the trigger pulse's low time, so the rate sets it. `status` and `set sync fsync` print that fact, the capture stack's loop drives gain alone, and `set exposure`, `set sync fsync --exposure` and a declared `camera.exposure_us` are refused with that fact. Under free run a declared `camera.exposure_us` without `camera.gain_db` is refused naming the capture stack's loop.
- `nxs <port> status` prints each pod's camera personality with its last run, `never run` before the first, and the line time and frame length that run achieved. The sensor's status rows come from probes the unit serves.
- `ros2 launch "$(nxs ros2 --launch-file)" cameras:=true` publishes the frames of each camera link that is up on `/nxs/<port>/<link>/image_raw` and `camera_info`, through the GStreamer camera node.
- `camera_encoding:=` picks `yuv422` (the default), `mono8`, `rgb8` or `jpeg` from the host's hardware encoder. `camera_source:=argus` uses the Isaac ROS Argus node where it is installed.
- `nxs.cam.frames(port, link)` yields a link's frames in Python as HxWx3 uint8 arrays with the frame's presentation stamp, with no ROS. It needs numpy and the GStreamer Python bindings on the host.
- `nxs::cam::Frames(port, link)` in `libnxs` hands a C++ program each frame as the platform's device buffer (an NV12 dmabuf on Jetson) with the sensor's timestamp, exposure and gain. On JetPack 7.2.1 a session reports `EIO` on the first frame, so the ROS 2 topics and `nxs.cam.frames` are the frame paths there.
- `nxs::cam::Frames` runs a synced pair's link as the tool's consumers do: the capture record carries the link's part, and the Argus session holds its loop at the pair's gain, a follower's read from the port's follower heartbeat as the session opens, without ISP digital gain, noise reduction or edge enhancement. `nxs.h` adds `nxs_capture_pair`, `nxs_capture_pair_of` and `nxs_frames_open_pair`; `nxs_capture`, `nxs_capture_of` and `nxs_frames_open` are unchanged, and `nxs_capture_of` answers `ENOTSUP` on a synced pair's link.
- `nxs personality check` and `nxs personality install` take a camera personality. An installed one extends the descriptor pack, so `nxs <port> caps` lists its modes and `suite.yaml` may name its sensor.
- The `generic` law family, for a camera whose modes run at the rate their register tables set. It runs one camera behind the hub. Another rate, frame sync or a second camera is refused.
- `CameraSensor` in the personality DSL, with `write_table()`, `load_table()`, `poll()`, `select()`, `check()` and `retry()`. The compiler that builds sensor personalities builds camera personalities too.
- A camera personality computes register values from the parameters staged for its run. `param()` reads one, `write_wide()` writes a result and `store_param()` records what the run achieved. The compiler refuses an expression that can overflow, underflow or divide by zero.
- The `nxs-generate-camera-personality` skill writes a camera personality from a datasheet and the vendor's register setting file, then compiles it.
- `nxs --experimental` reads a descriptor pack root and its experimental overlays (`$NXS_CAM_DESCRIPTORS`, `$NXS_CAM_EXPERIMENTAL`) and takes a development personality store. Nothing under the flag is part of the product.
- JetPack 7.2.1 (Jetson Linux 39.2.1) on the Jetson Orin Nano developer kit, beside JetPack 6.2.1. The boot table install finds the module's base DTB on either release.
- `nxs assets install` fetches the assets tarball of the tool's own version from the release page, asks once to accept its licence and installs it under `/opt/aliensense`. `nxs assets install <file>` takes a downloaded tarball, and `--accept-license` answers the prompt for a script.
- The tool refuses installed assets of another release and names the assets tarball of its own version.
- `nxs switch` realizes camera ports. It brings each declared pod to its declared personality and installs the port's boot table when the booted table lacks a declared mode or lane count. It then prints `REBOOT NEEDED` and exits 3.
- On JetPack 7.2.1, `nxs switch` and `nxsd` build the capture stack's configuration for the booted table, one short capture per mode, and keep it in the state store under the table's digest. A table seen before is installed without a build. `nxs <port> status` reads `preparing the capture stack` while a build runs.
- The capture stack's configuration build folds in the sensor vendor's ISP override, fetched once by URL and checked against the digest the descriptor names. An offline host copies the file to the place the refusal line names.
- `nxs switch` updates every declared unit that has no `firmware:` pin to the firmware in the installed assets.
- `nxs switch` restarts an `nxsd` of another build and prints `host: nxsd restarted (<old> -> <new>)`.
- `nxsd` on a host with no declaration waits for one instead of exiting, which restarted it every 5 s. It logs `no manifest at /etc/aliensense/suite.yaml; holding for SIGHUP`, and the reload `nxs switch` sends makes it read the declaration and bring the declared ports up. `nxs switch` hands the ports to `nxsd` for the host's declaration alone. A declaration that `-c` names elsewhere is brought up by `switch` itself.
- On JetPack 7.2.1, `nxs switch` and `nxs <port> status` name NVIDIA's camera hotfix when its files are missing, before any build.
- `nxs switch` and `nxs <port> status` name a missing kernel package first, `no camera kernel package for <kernel>`, with the `apt install` line under it.
- `nxs generate --json` prints the walk as data. The MCP server gains a `generate` tool.
- `nxs tune --schema` prints the rig's rules as JSON Schema: the manifest schema narrowed to the nodes on this rig. The MCP server gains a `suite_schema` tool.
- `nxs tune` marks 30 fps, 60 fps and the mode's ceiling on the fps knob as detents, labelled `· shipped`, and pulls a step that lands within 2 fps onto one.
- The MCP server gains an `upload` tool that compiles a personality and uploads it to a unit.
- `nxs <port> caps` marks the rates below a mode's guaranteed frame, `below 80.13 fps: beyond the datasheet's guaranteed frame (20.7.1)` for the 1920x1080 pair on 2 CSI lanes: a slower rate stretches the frame past the datasheet's recommended one. `--json` carries the rate as `fps_guaranteed`.
- `nxs <port> on`, `set sync` and `set fps` end on a delivery check: every camera link they ran is counted for two seconds at the rate it runs, through the capture stack. A link that misses a frame, reports a capture-stack error or delivers more than 1 % off the rate is refused with the rates delivered, `cam0: 60 fps asked, 58.1 delivered on A, 57.9 on B`, naming the highest lawful whole rate at or under the lowest (`nxs cam0 set sync fsync --fps 57`), or the lowest lawful rate when delivery fell under it. `on` then leaves the links unknown, and `set` puts back the sync or the rate that ran before. The check stops the tool's own viewers on those links first.
- `nxs <port> status` prints the last delivery check that passed under the sync line, `cam0: verified 30.0 fps 12 s ago (A 30.0, B 30.0)`, and `--json` carries it as `verified`. `nxsd` logs it after it brings a port up.
- `nxs <port> on` finds the line a pair behind the hub needs on the rig. It reads the hub's line-memory overflow probe around the delivery check and, where the probe reports an overflow, retimes the pair 5 % longer, from the deserializer datasheet's line up to twice it; past that it refuses with `cam0: the line memory overflows up to 1458 clocks` and names `csi_lanes: 4`. A count that falls short with the probe clear is refused at once with the delivered rates, and a rate the longer line no longer carries is refused at that step. The port record keeps the line found: `set`, `caps` and `status` judge the port at it, `caps` prints `[pair line 10842 ns, found]` and `--json` names its `line_source` `found`, and `status` prints `line 805` beside the verified rate.
- The hub's descriptor states the deserializer datasheet's facts the laws use, each with its section: the CSI bandwidth factor of 1.16 (Table 7), the 32 kB line buffer of each video pipe, and the minimum blanking of 40 pixels or 300 ns + 370 UI. A sensor mode states its datasheet register-list row with its section: the recommended frame V_TR, the line length and the rate at them.
- A frame-synced pair runs one gain. The leading link's capture session decides it, and `nxsd` copies it to the other head every frame under the sensor's register hold while the port runs frame sync with both links up. The journal reads `cam0: B follows A at 30 fps`, and `cam0: B stops following A (<reason>)` when the port runs free, parks, changes its rate or reloads.
- On a synced pair's links the viewers, `capture`, `nxs.cam.frames` and the ROS 2 camera node run with no digital gain, noise reduction or edge enhancement, each with its own white balance; the HUD names the link's part.
- `camera.gain_db` locks a synced pair's gain at one declared value, written once by `on`; under free run it locks the pair together with `camera.exposure_us`.
- `nxs <port> status` names who decides a pair's gain under the sync line: `cam0 ae: A leads, B follows (nxsd copies the gain each frame: 21.4 dB on both)`, a declared lock with the exposure it runs, or each link's own loop. A followed pair whose gain `nxsd` does not copy prints `cam0/B: does not follow A (nxsd copies no gain for cam0)` with `sudo systemctl restart nxsd` under it and exits 1. `--json` carries the same as `ae`, and a bare `nxs status` names the gap under the port.
- `suite.yaml` may be written as JSON. It loads the same as YAML.
- Sample FIFO. The unit queues every sample and the host reads them in batches over I²C, so a stream loses nothing while the host is late by less than the queue. The default depth holds 85 IMU samples, 425 ms at 200 Hz.
- `nxs stream` over I²C drains the sample FIFO and reports lost samples.
- `nxs get fifo-depth` and `nxs set fifo-depth <N>` read and set the queue's depth, where 0 means all the storage holds. The Cyphal register is `aliensense.nxs.sample_fifo.depth`, and `nxs commission --save` persists the depth.
- `libnxs`, the runtime library, ships in each platform wheel with its C headers `nxs.h` and `Frames.h`. It holds the unit client over I²C, Cyphal/CAN and Cyphal/serial, the sample stream, time sync and the port bring-up. The `nxs` tool runs on it.
- Firmware: `CAM_RUN` runs a camera personality from a store slot on the pod's bus, and `CAM_ABORT` stops the run within 50 ms. `CAM_STATE` and `CAM_ERROR` report the run's state and errno.
- Firmware: a cursor written after the `SAMPLE_DATA` pointer reads a burst of queued samples. The device-parameter view (`DRIVER_SELECT = 4`) sets the FIFO depth over I²C.
- Firmware: `XFER_TYPE` 6 and 7 serve a camera personality's descriptor trailer, up to 2048 bytes.
- Firmware: the personality instructions `POLL_REG`, `PARAM_LOAD`, `PARAM_STORE`, `MUL_REG` and `DIVU_REG`.
- An offline bundle per Jetson Linux release, `nxs-<version>-bundle-<l4t>.tar.gz`, with the aarch64 wheel, the assets tarball and the kernel package.
- Each platform wheel carries the NXS Runtime Library License for `libnxs` as `nxs/_lib/LICENSE`. The Python code and the headers stay Apache-2.0.
- `NOTICE` lists the third-party parts of `libnxs`, the unit firmware and the bootloader with their licence texts. The wheel carries it, and the assets tarball carries it with `LICENSE-Apache-2.0` beside its own `LICENSE`.
- On a host that boots no camera bus, as a stock JetPack image does, `nxs switch` installs the camera kernel package's mux overlay under the generated boot label and asks for one reboot, with or without a declaration. A rig of pods alone needs the kernel package for this too. On such a host `nxs probe` and a declared port name `nxs switch` as the next step.
- The Interface Description states how `nxs.h` and the `--json` documents grow from 1.1.0 on: a released struct keeps its size and meaning, a new field arrives as a new struct with its own function, and a key added to a `--json` object comes with a new contract number.
- The pure wheel, `aliensense_nxs-<version>-py3-none-any.whl`, ships on PyPI beside the platform wheels. pip takes it on a host no platform wheel matches, so `pip install aliensense-nxs` gives a Mac the compiler and `nxs personality check` for the personality skills. It carries no runtime library.

### Changed

- A frame-synced port takes a whole rate of its mode's range that the trigger law and the lanes admit, judged as a free-running rate is; every rate a refusal names is a whole rate the command accepts.
- A synced rate whose pulse period is shorter than the trigger frame is refused with the datasheet's prohibited period, `cam0: trigger frame <N> lines take <t> ms at this line, the next pulse lands inside them (datasheet 20.7.3)`, naming the highest whole rate that fits.
- Every mode a camera personality's program carries runs without `--experimental`: `on`, `set sync fsync`, `caps`, `nxs tune` and `nxs tune --schema` offer it, and the `… is not shipped …` refusals are gone. The flag gates a pack root, its overlays and a development personality store alone. A port with no declared mode runs the largest mode its laws admit: 2064x1552 RAW12 for one global-shutter head on 2 CSI lanes, and 1920x1080 for the pair, whose program carries RAW10. `caps` marks a mode the unit's program does not carry `[no unit program]`.
- A pair in a RAW12 mode is refused naming the pair's program, `a pair runs the doubled RAW10 pixel path, so 2064x1552 RAW12 runs alone on the port`.
- A mode runs from the driver's minimum rate, 1.50 fps, to the ceiling its datasheet frame and the lane law give at the port's line; no measured point narrows the range. One global-shutter head at 1920x1080 on 2 CSI lanes runs up to 160.49 fps. A pair runs the line the deserializer's datasheet gives its two packets, 729 clocks for the 1920x1080 pair on 2 CSI lanes, where it runs 1.50 to 80.13 fps free-running and every whole rate from 2 to 80 fps under frame sync, triggered at the mode's recommended frame. A refusal prints the range's ends inside it, the ceiling rounded down.
- `nxs <port> caps --json` names each mode's line source, `datasheet`, or `found` for a pair line `on` found on the rig, and on a pair lists the lowest and the highest whole rate frame sync runs each mode at.
- `nxs <port> caps` on a pair lists a range, a line and a sync pair for the modes both heads run together on the port's table alone: a mode the pair's program does not carry reads `[runs alone on the port]`, and a mode the table boots no row for reads `[no capture row]`; `--json` carries `runs_alone` and `capture_row`.
- A port that declares no rate runs 30 fps, inside its mode's range. The capture table's rows top out at the mode's own ceiling, the lower of its datasheet frame and one camera's lane ceiling on the port's CSI lanes, and default to the declared rate, 30 fps when none, never past that ceiling: a change of the declared rate moves the rows, and `nxs switch` installs the port's overlay and asks for a reboot.
- The capture table's rows come in a new order, so the first `nxs switch` after an upgrade installs each camera port's overlay again and asks for one reboot.
- The lane law counts the deserializer datasheet's minimum blanking on every line, the line that times a pair: one 1920x1080 RAW10 camera fills 2 CSI lanes at 188.87 fps (4 at 346.11), and the pair's lane ceiling is 94.44 fps. The datasheet frame binds first for the shipped modes, so their ranges stay.
- `nxs <port> off` and `stream` name only the viewers they stopped.
- `nxs <port> set sync fsync` states the filler rows the viewers crop under the trigger, `viewers crop the trigger frame's filler rows (97 lines, datasheet 20.7.3)`, from the pack's output-delay law.
- `nxs <port> on --mode` with a mode the port's capture table boots no row for is refused before any write, `cam0/A: 2064x1552 RAW12 boots on no row of this port's table (the table carries one pixel format, RAW10, chosen by the declaration)`, naming the declaration that carries the mode and the modes the table carries.
- A command waits up to a second for another's hold on the bus; `stream` and `capture` hold it only while switching the capture gate.
- `camera_source:=argus` is refused on a synced pair's links.
- `nxs <port> set gain` and `set gain_db` on a pair whose links run one gain are refused. The refusal names who decides the gain and `camera.gain_db` as the way to set it.
- `nxs <port> off` and the park `nxsd` runs have each pod park its camera after the host's park sequence, `pod B: park (<personality>, slot 1)`, so a parked unit's LED stops beating for the camera. A pod the tool cannot park prints one line, such as `pod A: no park run (no answer)`, and the port still parks.
- An addressed `nxs status` over I²C names the camera personality the unit holds under the sensor personality's lines, with its slot and last run: `Camera: <personality> (slot 1, last run DONE)`, `never run` before its first run, or `Camera: (none)` when the store holds none.
- Where `/boot/dtb` holds several kernel DTBs, as on JetPack 6.2.1, the boot table install takes the one that declares the booted module's compatible. When none or several match, the refusal names the files and `nxs switch --fdt <dtb>`, which names the base DTB by hand and is refused when the path names no file.
- On a camera host the declaration is `/etc/aliensense/suite.yaml`, which `nxsd` reads: `nxs generate` writes it there, `nxs switch` creates the directory group-writable for the `i2c` group, a declaration left under `~/.config` is refused by `switch`, `status`, `probe` and `generate` with the move that fixes it, which makes the directory first where it does not exist yet, and `nxs tune` saves a declaration the user cannot write through the sudo helper.

### Removed

- The host capture-budget warning of `nxs <port> set sync fsync`. A synced rate is judged by its mode's range and the laws of its sensors and the hub.
- The shipped points. A mode carries no proven operating point, in the descriptor, on the unit or in `caps`, and the SHIPPED trailer record (type 9) is retired: no compiler writes it, every decoder skips it and its number stays reserved.
- The measured laws: the serializer's pixel tail, the hub's pulse fraction, the lane-efficiency factor, the trigger fit, the readout resonance orders, the clean frame and the jump threshold, and the measured output delay. A law states a datasheet fact with its section, or arithmetic from such facts; the triggered viewers crop the datasheet's output delay, and the delivery check measures the rest on the rig.

### Fixed

- Frame sync on a port with a pod on each link converts both heads: the trigger program is written at each head's own host address, where a single broadcast address reached one head only.
- Frame sync runs one generator pulse per frame; a generator at a multiple of the frame rate ran the global-shutter heads at 77 fps at a 30 fps request.
- `nxs status` and `nxsd` judge a declared frame sync without a rate at the 30 fps `on` runs it at, and `on` refuses an unlawful synced rate before its first write.
- `nxsd` reconverges a port whose link rate, clock or exposure changed in the declaration.
- `nxs <port> status` and the `nxs tune` tree print a synced link at the generator's rate, where they printed the free-run rate `on` recorded.
- `nxs status` judges a link with no declared mode at the mode `on` runs, the highest its port admits.
- A refusal of `nxs <port> set` starts with the port's name, the laws' own included: `cam0: link A: 90 fps is outside …`.
- A capture table carries one pixel format as it carries one Bayer phase; a 2064x1552 RAW12 row no longer boots first on a 1920x1080 RAW10 port.
- `set sync free_run` keeps both links' video on a pair with a pod on each link.
- `nxs switch` brings a running port up again when any part of its declaration changed (rate, exposure, gain, sync, lanes), not only a link's sensor or mode.
- The following link's capture session starts at the leading link's current gain, so its first frame is not at 0 dB.
- A reload of `nxsd` brings a port back to its declaration when the port runs away from it: brought up by hand with `--mode`, `--fps`, `--sensor` or one link alone, or recorded by another build. `nxs switch` waited two minutes for such a port and failed.
- The capture stack's configuration is built after the port's heads stream, so a fresh hub's first boot with a new table configures; `switch` and `nxsd` no longer build it before the port comes up.
- The status LED beats for a camera run as it does for a measuring Click personality, and shows a camera head that does not answer or a faulted camera run as it shows the sensor's faults. It beats once for each running job, so a unit that measures and runs a camera shows two heartbeats back to back. A camera head its unit parked in standby does not beat.
- The boot entry carries the overlays of the declared ports alone. `nxs switch` and the `on` of a declared port drop the overlays of a port the manifest does not declare, print `dropped <file> from aliensense_gen: port cam0 is not declared` for each, and ask for the reboot. A Hub moved from cam0 to cam1 left cam0's overlays in the entry, and their capture nodes put the capture stack's sensor numbering out of step with the tool's.
- `nxs switch` ends its wait on `nxsd` as soon as the daemon's bring-up of a port stops short. A port that needs a reboot ends the run with the daemon's lines and `REBOOT NEEDED`, exit 3, and a refused port ends it with the refusal, exit 1. `switch` waited 120 s for such a port and printed `cam1: nxsd did not bring the port up in 120 s`. A reload of `nxsd` brings up again a port whose last bring-up stopped short.
- `nxsd` holds for a reload when the manifest is out of tune with the host at start, such as a lane count the booted tree does not carry before its reboot. It logs the findings once per check, and `nxs switch` prints them as each port's refusal. `nxsd` exited 1 on such a manifest, and systemd restarted it every 5 s until the reboot.
- The capture stack's configuration a port installs from the state store is one built for that port. A Hub moved from cam0 to cam1 with the same table got the configuration built for cam0, and the capture stack refused every session on cam1. The store keeps each configuration under its port and table, so the first `on` on cam1 builds cam1's own. After an upgrade each camera port's first `on` builds its configuration once more, about two minutes.
- A capture row tops out at its mode's datasheet ceiling where one camera's lane ceiling lies above it, 160.49 fps for the global-shutter head's 1920x1080 row on 2 and on 4 CSI lanes. A four-lane row that took the lane ceiling left the capture stack's configuration build with no knob set for the mode, and `on` refused. The rows move, so the first `nxs switch` on a host that booted the earlier rows installs each camera port's overlay again and asks for one reboot.
- A boot table install the host refuses, such as one with no base DTB to name, ends `nxs switch` and `nxs <port> on` with the refusal and exit 1 instead of `REBOOT NEEDED`. `nxs switch` prints the files the install writes.
- When the boot entry `nxs switch` wrote has booted and no camera bus came up, `nxs switch` stops with `host: the boot entry aliensense_gen booted without its overlays`, prints what `fdtoverlay` says of the multiplexer overlay on the entry's device tree where that tool is installed, and names `nxs switch --fdt <dtb>`, instead of asking for the same reboot again. The entry's kernel command line ends with `aliensense_label=aliensense_gen`, which tells it apart from the other entries, and `--fdt` naming another device tree rewrites it.
- A declared `csi_lanes` wins over the lane count the host booted. Where the booted camera table has another count, `nxs switch` installs the declared count's table and prints `REBOOT NEEDED`, instead of leaving `nxs <port> on` to refuse the mismatch. Without a declaration the booted count stands.
- After a power cycle of the camera hub, `nxs switch` brings the port up again, which maps the pods' aliases, instead of stopping at `no pod answers at 0x31`. A pod alone behind its hub is brought to its personality at the address it straps first. A pod that answers nowhere is named with both addresses: `cam0/A: no pod answers at 0x31 or at 0x30 (unit-cam0-a)`.
- `nxs <port> on` names the link and the addresses it tried when a pod's store does not read, `cam1/B: no pod answers at 0x32 or at 0x30 (peek slot 0: Remote I/O error)`, where it printed `up: [Errno 121] Remote I/O error (peek slot 0)`.
- `nxs <port> on` probes a link that does not lock at 6 Gbps again at 12 Gbps, issuing the window one-shot a second time before it gives up, and says what it found: `serializer already programmed: locks at 12 Gbps`, or `no lock at 6 or 12 Gbps: serializer absent, or programmed on a link that does not carry 12 Gbps`.
- The boot label `nxs switch` and `nxs <port> on` write names only overlay files that exist. The install drops an entry for a missing file, since the boot launcher skips every overlay of a label that names one, and prints the entry it dropped.
- The `/boot` writes, the capture daemon's restart and the capture stack's configuration build ask for the password in a terminal, as the tool's other root steps do. Without a terminal sudo refuses at once, and the refusal names sudo's answer and `run it in a terminal`.
- On JetPack 6.2.1 `nxs switch` and `nxsd` build no capture-stack configuration, and `nxs <port> on` and `nxs <port> status` ask for none: Argus on Jetson Linux 36 has no configuration mode and streams on its built-in tuning.
- A port whose declaration and booted tree name no CSI lane count takes its connector's on the Jetson Orin Nano developer kit: 2 on cam0, 4 on cam1.
- A camera run that ends before the host reads its accept reports the run's verdict with its state, `camera run FAULTED: …`, instead of a slot that holds a driver personality. A program larger than the unit's camera runner, an error the personality raises, a bus clock it cannot run at and a register read it does not expect each carry their own reason; a personality that does not parse reads `EBADF` (reinstall it: `nxs switch`) and a program that faults `EFAULT` (the unit's log names the instruction), never a driver slot's `ENOEXEC`. The `CAM_RUNS` diag counter counts the accepted runs, so a run that ends inside the host's hold-off reads as this run's verdict even when it ends the way the previous one did. `nxs.h` adds `nxs_unit_read_cam_runs`, which reads the count, and `nxs_unit_diag` is unchanged.
- A camera personality upload prints the slot it lands in and advises no `nxs store save`, since the upload saves it. A transport that cannot save one refuses the upload before the image crosses, and the help of `nxs store save` reads `Save the last upload to a flash slot`.
- `nxs status` counts the personalities the assets ship beside the installed ones, `(2 shipped, 0 installed)`, and `--json` carries `shipped`.
- `nxs generate` seeds each unit with the personality it runs, `sensors: [{personality: fxos8700}]`, for a pod behind a hub link as for a unit on a bare bus, so the first `nxs switch` keeps the personality the unit shipped with. A unit that runs no personality the tool knows gets no `sensors` key, and `nxs switch` leaves its store alone.
- `nxs <port> status` and `nxs status` wait up to 20 s for a bus that another run holds, as `nxsd` does while it brings the ports up after boot, then name the run instead of a hub that does not answer; `nxs status` reads a unit on a port's bus under the same lock and wait, and names a held bus on the unit's row instead of `NO ANSWER`. A hub that misses its first read is read again 100 ms later.
- `nxsd` waits up to 20 s for a bus another run holds, at construction and at a reload's reconverge, instead of failing the port's step.
